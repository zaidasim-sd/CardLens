## Exact data flow

1. User selects/captures an image; the browser prepares a card crop. File selection/camera alone does not invoke an OCR provider.
2. Scan sends the prepared image to `/api/ocr` on the service origin. The backend forwards the image to Google; on an exception or absent primary key, `both` mode forwards it to OCR.space if configured. The same image may reach both. Provider receives content visible in the image, not merely the eventual selected form fields.
3. Backend parses returned text locally using `cardParser.js`; there is no additional LLM/contact enrichment call in the inspected processing path. It returns text and parsed fields to the browser.
4. Review is transient until submission. Saving stores submitted image, filename, raw text, original parsed fields, reviewed fields and metadata in IndexedDB. Reviewed alternate phone, website, address and city are blank in the current save path, but original extracted values may remain in raw text/`ocrData`. Notes are also copied into `meetingContext.notes`.
5. Built-in demo and manual entry bypass OCR. Local duplicate checking may expose existing records. There is no server contact save, shared review workflow or external transfer after submission.
6. The unused XLSX helper would export: Record ID, Full Name, Job Title, Company Name, Email, Phone, Alternate Phone, Website, Address, City, Country, Notes, Verification Status, Scanned At and Verified At. It does not export images, raw OCR or the separate meeting-context object. This is a potential file layout, not a Constant Contact mapping or active transfer.
