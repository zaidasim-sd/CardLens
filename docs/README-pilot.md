# CardSnap internal architecture pilot

This is a working preparation build, not an approved production service. It accepts fictional records only and refuses `APP_ENV=production`. Public React routes show only a fixed fictional card. The original scanner components remain in source, but are not exposed by the public app.

## Run locally

Requires Node 24 (uses `node:sqlite`). From the repository root:

```powershell
npm ci
# On a fresh installation, copy .env.example to .env and configure secrets.
npm run pilot:setup
npm run pilot
```

Open http://localhost:3000/pilot/. Local demonstration accounts are in ignored `.data/demo-accounts.json`. They represent separate assistant, reviewer and administrator personas; provision individually named users for the actual team. Do not share the demonstration passwords as production accounts. The supplied Constant Contact test app credentials were configured in ignored `.env`, not frontend code. The encryption key is also there. Protect and back up this key separately from encrypted backups.

The local OCR adapter uses Tesseract.js and downloads the English model on first use. It processes images locally. Set `OCR_PROVIDER=google` and a server-only `GOOGLE_VISION_API_KEY` to exercise the proposed Google adapter after provider approval. It has not been validated against a paid cloud account. OCR is always a suggestion; corrections must be saved before submission.

## Demonstrate

1. Assistant: sign in, complete the fictional-data form, save a draft, upload a fictional PNG/JPEG from `validation/ocr`, review the extraction and save corrections, then submit.
2. Reviewer: inspect the central queue and any duplicate candidates. Approve, request correction, reject or archive. A distinct-contact decision never overwrites a destination record.
3. Reviewer: transfer an approved record. Success stores a Constant Contact ID. Failure remains visible. A timeout/5xx after a possible write requires lookup and explicit linking of a verified existing ID, not another blind POST.
4. Administrator: manage users and dropdowns, reduce retention, connect the confirmed test account and select exact destination list/custom-field IDs.
5. Support: create a named support user with expiry no more than 24 hours away. Support can view aggregate counts only.

OAuth uses the exact registered localhost callback in `.env`. Client ID and secret identify the integration; the account owner must also sign in and consent. The live test used an isolated `CardSnap Readiness Test 2026-09-24` list because `General Interest` was absent, and reused `Lead Source`. It created one fictional contact, verified mapping, refresh, duplicate conflict and repeated-transfer behavior. See `validation/constant-contact-live.json`. No email campaign API is implemented or invoked. Supplied sender settings remain unused.

## Verification

```powershell
npm test
npm run build
npm run lint
node scripts/smoke-pilot.js
npm run test:ocr
```

The smoke script creates fictional local records and runs actual OCR. The separate `node scripts/validate-constant-contact.js` script changes the user-confirmed test account: it creates/reuses an isolated test list and Lead Source field, creates one fictional contact per run, and checks provider and application duplicates. Never run it against a client account. It does not send email or update existing contacts.

The 30-card corpus is generated by `scripts/generate-ocr-corpus.py` (Pillow). Results measure exact normalized fields after OCR and parsing, including three additional back images. `baseline-results.json` preserves the pre-fix result; `results.json` is the final run. These are synthetic layout/degradation tests, not representative real-camera acceptance testing or a blind holdout. Manual-correction count is inferred from comparison to expected values, not a timed human study.

## Retention and recovery

Default image retention is 24 hours, configurable from zero to 168 hours. Zero means do not persist images. A worker deletes expired images on startup and every minute. Reducing retention shortens existing deadlines. Images are encrypted in the central SQLite database; no public URL exists. Metadata, payload validation and complete image decode enforce PNG/JPEG, 2 MiB per side, two sides, at most 6000 pixels per dimension and 20 million pixels. Explicit deletion and retention deletion are audited. Secure-delete and checkpointing reduce old SQLite page remnants, but infrastructure snapshots and disk disposal need production controls.

```powershell
node scripts/backup-pilot.js backup .data/backup.enc
# Stop destination service first. Restore to a new, empty database with the SAME DATA_KEY.
$env:DATA_PATH='./.data/restored.sqlite'
node scripts/backup-pilot.js restore .data/backup.enc
Remove-Item Env:DATA_PATH
```

Backup encrypts the full export and excludes images, sessions and pending OAuth state. Restore was exercised to a fresh database: three users and one record restored, zero images/sessions. Backup files include encrypted integration tokens, so restrict access. Rotate/reconnect credentials as needed after recovery. Automated remote backups, separate-key custody and recovery-time acceptance are not deployed.

An interrupted transfer leaves a durable tenant lock. Stop the service, inspect its non-PII audit and destination contact by exact email, explicitly reconcile the receipt, then release the tenant lock under a documented administrator maintenance change. Do not remove the lock while a transfer could still be running. If no destination record can be confirmed after an uncertain write, escalate; this build intentionally does not automatically retry that write. This prioritizes avoiding accidental duplicates over unattended recovery.

## Production gap and deployment plan

`config/*.env.example` separates development, staging and production keys, origins and data paths. These are templates, not deployed environments. Keep independent test integrations, databases and secrets for staging. The checked-in Vercel configuration is for the static prototype only; it cannot host the durable pilot database/worker.

Deploy the eventual pilot behind HTTPS with private database/storage, managed key custody, remote backups and monitoring. This demonstrator uses one Node process and application-enforced tenant scoping over encrypted SQLite entities. Before a multi-instance release, migrate to a transactional managed database with tenant foreign keys/RLS and a durable outbox/lease worker. Implement SSO/MFA or reviewed password lifecycle, idle timeout, external alert delivery, immutable audit export and production operations tests. Do not merely remove the production lock.

No Salesforce replacement, historic contact import, campaign sending, follow-up task system, religion field or relationship intelligence is included. Short notes still require user guidance to avoid entering sensitive personal information. The pilot validates allowed structured fields but cannot reliably infer whether arbitrary text contains sensitive information.
